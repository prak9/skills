# Governance Domains & Persistent Artifacts

在 Phase 1 建图与 Phase 2 逐域排查时读取本参考，避免凭感觉零散重构。

## Twelve Governance Domains

按代码库实际情况裁剪适用域，逐域识别熵增并录入任务池：

| # | 治理域 | 典型熵增信号 | 收敛目标 |
|---|---|---|---|
| 1 | UI 组件与设计系统 | 同语义多套按钮/表单/弹窗、散落的硬编码样式 token、组件内混杂业务请求 | 唯一设计 token 与基础组件源；展示组件与业务逻辑分离 |
| 2 | 业务逻辑与领域模型 | 同一规则在多处复制判断、贫血 DTO 与隐式状态机、领域逻辑散落在 controller/UI | 领域规则收口到权威模型/服务，修改一处即全局生效 |
| 3 | API 接口与数据契约 | 同资源多版本/多风格端点并存、手写重复 schema/类型、未声明的隐式字段 | 单一契约源生成或校验类型与序列化边界，保留有真实消费者的兼容契约 |
| 4 | 状态管理与数据流 | 同一份数据在多处缓存/镜像、双向同步副作用、跨组件隐式共享可变状态 | 明确每份状态的唯一写入所有者与单向派生数据流 |
| 5 | 数据访问与缓存 | 散落的裸查询、多套 ORM/client 并存、缓存失效逻辑分散且不一致 | 统一仓储/数据访问边界，缓存读写与失效策略内聚在同一模块 |
| 6 | 配置与环境变量 | 各处直接读 `process.env`/`os.environ`、默认值散落且相互冲突、未校验启动配置 | 单一启动配置解析与强类型校验入口，下游只消费已校验配置对象 |
| 7 | 错误处理与重试机制 | 吞错/空 catch、跨层错误码不统一、局部手写不一致的重试与退避 | 统一错误分类与边界转换，幂等与重试策略收敛到标准封装 |
| 8 | 日志与可观测性 | `console.log`/`print` 与结构化日志混用、上下文追踪字段缺失、指标命名混乱 | 统一结构化日志与 trace 注入，消除噪声输出 |
| 9 | 权限与身份认证 | 鉴权判断分散在各 handler、角色/权限字符串硬编码、默认放行隐患 | 鉴权策略收口到声明式中间件/策略中心，默认拒绝 |
| 10 | 命名、目录结构与模块边界 | 同概念多种命名、循环依赖、跨层直连内部实现、`utils` 垃圾桶膨胀 | 清晰的分层与导出面（barrel/internal 边界），禁止绕过公开接口 |
| 11 | 工具函数与公共基础设施 | 同功能多个时间/金额/字符串 helper、复制粘贴的轻包装、过时 polyfill | 合并为少量高内聚标准库或直接用语言原生能力，删除薄转发层 |
| 12 | 测试、构建与开发工具链 | 多套测试/打包/lint 配置并存、脆弱的内部实现 mock、本地与 CI 命令不一致 | 单一标准构建与验证入口，测试聚焦可观测契约与真实行为 |

## Persistent Tracking Artifacts

在隔离 worktree 中维护轻量、可恢复的治理记录（默认放在不污染生产构建的追踪目录，如 `.arch-deentropy/`；仅在用户明确要求归档时纳入正式提交）：

### 1. 基线地图（`maps.md`）
- **架构与依赖地图**：核心模块清单、允许的依赖方向、当前循环依赖与跨层违规列表。
- **状态所有权地图**：状态名称 → 唯一所有者 → 读写入口 → 发现的重复镜像/共享可变源。
- **平行实现与规范偏离清单**：语义/能力 → 现有实现列表（含调用方数量）→ 拟定权威实现 → 偏离说明。

### 2. 优化任务池与进度（`backlog.md`）
每条任务记录最少字段：
- `ID` / `治理域` / `熵增类型`（重复实现 | 循环依赖 | 浅抽象 | 状态泄漏 | 规范偏离 | 缺失门禁）
- `影响面`（调用方数 / 模块数）与 `风险等级`（低 / 中 / 高）
- `状态`：`todo` | `active` | `done` | `pending-decision`
- `验收证据`：commit SHA、测试命令结果、新增防回归规则路径
- 若为 `pending-decision`：注明所需产品/架构决策点、备选方案与阻塞边界，不影响其他独立任务继续推进。

### 3. 架构决策记录（`adr.md`）
仅记录有长期意义的架构裁决（不为琐碎重构写八股）：
- **背景与问题**：为何存在熵增或分歧。
- **备选方案与 Deletion Test 结果**：对比至少 2 个方案的总复杂度与抽象层是否通过 Deletion Test。
- **最终选型与权衡**：为何该方案总复杂度最低；明确不做什么。
- **防回归门禁**：已落地的类型/Lint/AST/契约测试/CI 约束。

## Batch Sizing & Worktree Discipline

- **隔离 worktree**：从当前基线分支创建独立 worktree 与治理分支（例如 `git worktree add ../<repo>-deentropy -b refactor/arch-deentropy`），避免污染主工作区。
- **批次粒度**：每批聚焦一个可完整闭环的语义主题（例如「统一配置入口并删除散落 env 读取」或「合并两套日期格式化工具并加 lint 禁令」），做到单批可独立回滚、单批可独立评审。
- **先删后加优先**：若可直接删除冗余层或回归语言/框架原生能力，优先删除而非新增抽象。
- **独立复审清单**：每批提交前对照核查：
  1. 被替代的旧实现是否已彻底删除，无孤立死代码或“以防万一”的兼容壳？
  2. 新留存的每一层抽象是否通过 Deletion Test？
  3. 是否存在把语义不同的逻辑强行合并的伪统一？
  4. 新增自动化门禁是否经过“先拦住违规、再放行合规”的验证？
